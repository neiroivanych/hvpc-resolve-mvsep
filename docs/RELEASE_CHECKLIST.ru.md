# Подготовка HVPC Resolve-MVSEP к публикации

Этот документ предназначен для автора выпуска. Пользовательские инструкции: [RU](../README.md) и [EN](../README.en.md).

## Что уже подтверждено

12 октября 2026 года пользователь подтвердил, что финальные ручные тесты выполнены и поведение соответствует ТЗ. Этот этап принят. Проверка установки ниже проверяет только получение и настройку чистой копии, а не повторяет весь функциональный аудит.

14 октября 2026 года пользователь подтвердил проверку чистой установки из подготовленного ZIP:

- разделение работает в прежнем и новом проектах Resolve;
- обработка продолжается после закрытия Resolve во время разделения;
- после повторного открытия проекта результаты добавляются в Media Pool и на новые аудиодорожки.

Проверка чистой установки пройдена. Восстановление рабочей установки пользователь выполняет по инструкции; оно не является условием публикации. Код в `src/` и `scripts/` сверен с проверенным архивом от 12 октября: изменений нет. Дальнейшая подготовка выпуска затрагивает документацию и состав публичных файлов.

## Первый публичный выпуск

Используется существующая версия пакета **0.2.0**, тег **v0.2.0**, название выпуска **HVPC Resolve-MVSEP 0.2.0**. Для первого публичного выпуска предлагается отметить **This is a pre-release**: ручные проверки пройдены, но проверенная конфигурация пока ограничена указанной в README платформой. Текст выпуска RU/EN подготовлен в [docs/releases/v0.2.0.md](releases/v0.2.0.md).

Предлагаемое имя репозитория: `hvpc-resolve-mvsep`. Владелец, видимость и фактическое размещение определяются перед публикацией. До загрузки на GitHub этот документ не подтверждает существование репозитория, тега, выпуска или успешного запуска GitHub Actions.

## Проверка файлов и создание чистого ZIP

Для подготовки архива нужны установленный Git и обычный Python 3.10+ с модулем unittest. Это инструменты автора выпуска; пользователю программы они отдельно не нужны. Встроенный ResolvePython может не содержать unittest.

1. Завершите редактирование кода и документации.
2. Откройте PowerShell в корне проекта и выполните:

   ```powershell
   python tools/prepare_release.py
   ```

3. При успехе команда покажет путь к новому ZIP в `build` и контрольную сумму SHA-256. Подробный список включённых файлов и результаты проверок находятся в `logs/release-audit.json`.
4. Если проверка остановилась, сначала устраните указанную причину. Не используйте старый архив как выпуск с новыми изменениями.

Команда применяет `.gitignore`, проверяет отсутствие личных папок и медиа, известных локальных API-токенов и их URL-кодированных вариантов, персонального домашнего пути. Проверяются пустой токен в примере, настройки первого запуска, ссылки в README и синтаксис Python 3.10. Затем в отдельной временной копии выполняются тесты и компиляция. ZIP содержит только проверенный список; его содержимое повторно сверяется по SHA-256.

Локальные `config`, `settings.json`, `jobs`, `logs` (кроме пустого `.gitkeep`), `output`, медиа, персональный файл запуска, внутренние `NOTES.md` и `docs/AUDIT-*.md`, созданные архивы не входят в ZIP. Команда не создаёт Git-репозиторий в рабочей папке, не подключается к MVSEP и ничего не публикует.

Это проверка текущих файлов и известных токенов, а не всей истории Git или любых возможных секретов. Перед первым коммитом просмотрите включённые документы и файлы. Если Git уже отслеживает файлы, которые теперь игнорируются, команда остановится: одно добавление в `.gitignore` не удаляет их из отслеживания или истории.

## Установка с нуля на том же компьютере

1. Дождитесь завершения фоновых задач. Закройте Resolve и окна HVPC Resolve-MVSEP.
2. Сохраните резервную копию установленного `HVPC Resolve-MVSEP.py` из папки `Utility` **вне папки Utility**. Если задана переменная `RESOLVE_MVSEP_HOME`, запишите её прежнее значение.
3. Распакуйте проверенный ZIP в новую пустую папку, например `D:\Apps\HVPC Resolve-MVSEP Test`. Найдите внутри папку с `src`, `scripts` и README — именно она является папкой программы.
4. Не переносите туда прежние `config`, `settings.json`, `jobs`, `logs` или `output`. Следуйте разделу «Установка» нового README: создайте настройки из примеров и введите токен вручную из аккаунта MVSEP.
5. Установите файл запуска из чистой копии, указав её путь в `PROJECT_ROOT`. Если существует `RESOLVE_MVSEP_HOME`, на время проверки также направьте её на чистую копию. Перезапустите Resolve.
6. Откройте отдельный тестовый проект с коротким аудиофайлом. Убедитесь, что открываются настройки разделения, отсутствуют старые наборы и история, переключаются RU/EN, а папка результатов относится к новой копии.
7. Выполните одно короткое разделение с бесплатными настройками. Проверьте скачивание и добавление в Media Pool/на дорожки. Убедитесь, что файлы появились в папке новой копии. Полный набор монтажных сценариев повторять не требуется.
8. После проверки закройте программу и Resolve. Восстановите прежний файл запуска и прежнее значение переменной, если меняли его. Перезапустите Resolve и убедитесь, что снова открывается рабочая установка.

Установочная проверка считается пройденной, если чистая копия работает только с настройками, созданными по README, и не зависит от файлов рабочей установки. Альтернатива — другой компьютер с поддерживаемым Resolve Studio или отдельная учётная запись Windows.

## Перед загрузкой на GitHub

Используйте исходное содержимое проверенного архива **до установочного теста**. Папка, в которой уже выполнена установка, содержит токен и личные данные и не является чистым дистрибутивом.

1. Зафиксируйте номер версии и описание выпуска. Укажите проверенную платформу и статус предварительного выпуска, если это первая публичная версия.
2. Проверьте список файлов будущего коммита: пользовательские README, LICENSE, примеры без токена, исходники, тесты, инструменты подготовки и конфигурация GitHub Actions. Локальные конфигурации, журналы и медиа туда не входят.
3. При использовании Git проверьте список подготовленных файлов командой `git diff --cached --name-only`, затем сам diff. Не используйте принудительное добавление игнорируемых файлов. Если токен когда-либо попал в коммит, одного удаления из последнего состояния недостаточно: отзовите его в MVSEP и разберите историю до публикации.
4. После загрузки кода дождитесь успешной проверки во вкладке Actions. Локальный успех не означает, что GitHub Actions уже выполнялся.
5. Для раздела Releases прикрепляйте проверенный исходный ZIP, а не папку после пользовательского запуска. После любых изменений подготовьте новый архив.
